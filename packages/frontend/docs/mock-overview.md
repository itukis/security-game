# SecurePatch Quest mock概要

この資料は、SecurePatch Questの現在のフロントmockを初学者向けに説明するためのものです。実装ファイルを確認した範囲に基づいています。

## SecurePatch Questとは

SecurePatch Questは、AIが生成したアプリ画面やコードを題材に、セキュリティ上の弱点を見つけて修正する学習ゲームです。

現在のmockでは、新人ホワイトハッカーとして、AIが生成したログイン画面を診断します。SQL Injectionの弱点を疑似攻撃で確認し、原因コードを読み、修正案を選び、再テストで防御できたかを確認します。

## 誰向けか

- セキュリティを学び始めた人
- SQL Injectionを初めて学ぶ人
- AI生成コードの安全性に関心がある人
- Vibe codingでアプリを作り始めた人
- 「脆弱性を見つける」だけでなく「直す流れ」も体験したい人

## 解決したい課題

AIを使うと、アプリの画面やコードを短時間で作れます。しかし、生成されたコードが安全とは限りません。

初学者にとっては、次のような点が難しくなりがちです。

- どこが危険なのか分からない
- なぜ危険なのか分からない
- どう直せばよいか分からない
- 修正後に本当に安全になったか確認する流れが分からない

SecurePatch Questは、この流れをゲーム形式で学べるようにすることを目指しています。

## このモックで体験できること

現在のmockでは、SQL Injectionの1問を体験できます。

1. 攻撃テストを実行
2. ログイン認証が突破される疑似結果を確認
3. 原因コードを読む
4. 3つの修正案から1つを選ぶ
5. 修正後に再テストする
6. 防御成功または防御失敗を確認
7. 解説を読む

大事な点として、このモックは本物の攻撃やDB操作を行いません。画面上の結果は学習用の疑似判定です。

## 用語ミニ解説

### SQL Injection

SQL Injectionは、ユーザー入力がSQL文の一部として扱われてしまう脆弱性です。SQLはデータベースに命令を出すための言語です。

今回の例では、ログイン画面の入力値がSQL文字列へ直接結合されています。そのため、入力値が「ただのメールアドレスやパスワード」ではなく、「SQLの命令」として解釈される可能性があります。

### プリペアドステートメント

プリペアドステートメントは、SQLの形と入力値を分けて扱う方法です。

入力値をSQL構文ではなく値として扱いやすくなるため、SQL Injection対策として重要です。

### mock判定

mock判定とは、本物の処理を動かさずに、決められたデータで結果を返す疑似的な判定です。

このモックでは、正しい修正案を選んだ場合だけ防御成功にします。実際に攻撃したり、SQLを実行したりはしません。

### API

APIは、フロントエンドとバックエンドが情報をやり取りする窓口です。

将来的には、フロントからバックエンドAPIへpatchを送り、バックエンド側で検証結果を返す想定です。

### DB

DBはデータベースのことです。ユーザー情報や学習履歴などのデータを保存する場所です。

現在のモックはDBに接続していません。

### Monaco Editor

Monaco Editorは、VS Codeのようなコード編集体験をWeb画面に入れるためのエディタです。

現在は導入していません。コード表示は `CodeViewer` コンポーネントで分離しており、後から差し替えやすい構成です。

## SQL Injectionの例

危険なコードのイメージ:

```ts
const query =
  "SELECT * FROM users WHERE email = '" + email +
  "' AND password = '" + password + "'";
```

問題点:

- 入力値をSQL文字列へ直接結合している
- 入力値がSQL構文として扱われる可能性がある
- ログイン認証が突破される弱点につながる

疑似攻撃ペイロード:

```txt
' OR '1'='1
```

安全な修正のイメージ:

```ts
const query = "SELECT * FROM users WHERE email = ? AND password = ?";
const user = await db.query(query, [email, password]);
```

このように、SQLの形と入力値を分けるのがポイントです。

## このモックで本当に行っていないこと

このフロントmockでは、次の処理は行っていません。

- 本物の攻撃通信
- 本物のSQL実行
- 本物のログイン処理
- DB接続
- 外部サイトへのアクセス
- Dockerやバックエンド連携

攻撃成功や防御成功は、すべて学習用の疑似判定です。安全に流れを理解するための画面です。
